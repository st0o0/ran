## Design notes

- Reuse: `MCPTrap` embeds `HTTPTrap` (like `docker` and `kubernetes`) and uses `newStubRequest` for the bounded body, sanitized path and user agent, header subset and `claimed_client_ip`. Sessions are per connection.
- Parsing: `json.Valid` first (iterative, refuses more than 10000 levels), then the envelope is decoded with `any` for `jsonrpc` and `method` and `RawMessage` for `id` and `params`, so a wrong type is an invalid request (`-32600`) and not a parse error. Arguments are decoded into `map[string]json.RawMessage` only: nested values are never decoded, so nesting depth costs no recursion in our code. The 16 KiB body limit keeps a request below the decoder limit anyway; the limit is tested on the parser directly.
- Batch: more than 16 elements or an empty array is one `-32600` for the whole body (the JSON-RPC spec allows this for an empty array; the cap is our choice). Notifications (no `id`) get no answer; a body with only notifications gets `202`. A non-object element is an invalid request with id `null`.
- Ids: echoed only as small integers or short strings of safe characters, else `null`, so the response never carries client text. A string id is decoded, validated and re-encoded, not echoed raw, so JSON escapes cannot make the echo longer than 66 bytes.
- `tools/call` with unusable params (no string name) is still an `attack` and recorded with an empty tool name; the answer is the same plausible `isError` result. Unknown tool names get the same answer as known ones so the decoy does not reveal its tool table.
- Argument summary: keys sorted (JSON objects are unordered), first 8 kept. Values of keys that contain (case-insensitive substring) `password`, `passwd`, `pwd`, `passphrase`, `secret`, `token`, `api_key`, `api-key`, `apikey`, `access_key`, `auth`, `authorization`, `bearer`, `cookie`, `session`, `jwt`, `credential` or `private_key` are replaced by `***` in logs and meta regardless of `RAN_LOG_PASSWORDS`. The alert pipeline only drops meta keys of that name, not a `command` value that contains the secret, so string values and the command line are also scrubbed (`secretscrub.go`): `Authorization:`/`Cookie:` headers, `Bearer x`, URL userinfo, `--token x` style flags and `KEY=value` with a secret-like name become `***`. The alert meta (`command`, docker `image`, docker and kubernetes `command`) is always scrubbed; the log follows `RAN_LOG_PASSWORDS` like `redactCommand` (`on` keeps the text). Objects and arrays are never descended into, so nested keys never reach the summary. The log carries the full summary (at most 1552 bytes) as `arguments`; the `command` log field and meta are cut to 256 bytes by the shared sanitizer.
- Credential headers: `Authorization` (any scheme) or `X-API-Key` give an auth attempt with a hash prefix, as the kubernetes trap does for bearer tokens. A legitimate MCP client sends these too, but a public decoy has no legitimate client. `Mcp-Session-Id` is never issued by the decoy, so it is ignored.
- Routes: `GET /sse` sends one `endpoint` event and ends (a closed stream); `GET` or `DELETE` on `/mcp` is `405` as the streamable HTTP transport allows. Unknown paths are `404`. An oversized body is `413`, a probe and not logged.
- Metric label: `mcp` only (the trap name).
- Residual risk: scrubbing is name and shape based. A secret with no recognizable name or shape (a bare password argument such as `mysql -p hunter2`, a token passed positionally, a value in a free-form key like `data`, a secret split across arguments or encoded) is still recorded in the command text, which is cut to 256 bytes but sent to CrowdSec as meta. Attackers rarely bring real secrets to a decoy, so the risk is accepted; the scrub is deliberately over-eager (for example `author=x` is hidden because it contains `auth`).
