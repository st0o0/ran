## Decisions

- **Match rule.** A fixture is chosen by the exact, case-sensitive request path (`r.URL.Path`, already percent-decoded by `net/http`). The query is ignored. No prefix, glob or regex matching: it keeps the table auditable and makes it impossible for a crafted path to select a fixture by accident. Classification runs on the same path before the fixture is chosen and is not affected.
- **Where it hooks in.** After request logging, classification, Basic auth and body handling, and after the alert, `handleRequest` asks the fixture set to serve the request. The earlier steps are untouched, so a fixture hit is logged with the same fields as any request and `/.env` stays a command (`attack`) while `/robots.txt` stays a `probe`.
- **Methods.** Only `GET` and `HEAD` are answered by fixtures. `POST`, `PUT`, `PATCH`, `OPTIONS` and all other methods keep the existing login page behavior. This is the precedence rule for form logins: a fixture can never swallow a credential POST, even when an operator defines a fixture on `/wp-login.php` (the `GET` shows the fixture, the `POST` still captures credentials and returns the login error page).
- **HEAD.** Same status and headers as `GET`, `Content-Length` of the body that `GET` would send, no body. A `204` has neither body nor `Content-Length`.
- **Precedence.** Operator fixtures replace built-in fixtures with the same path. Neither overrides the non-fixture behavior of other methods.
- **File format.** JSON, stdlib `encoding/json`, no new dependency (YAML would need one). Shape: `{"fixtures":[{"path","status","headers","body"}]}` with `DisallowUnknownFields` and trailing data rejected. A top-level object (not an array) leaves room for later keys. Bodies are JSON strings (text only; there is no binary body support). `status` defaults to 200, an explicit value must be in a safe set (`200 204 400 401 403 404 500 503`; no redirects, so no `Location` header is needed). A `204` must have an empty body.
- **Header allow-list.** Content and cache related headers, `Server`, `X-Powered-By`, `X-Frame-Options`, `X-Content-Type-Options`, `X-Robots-Tag`, `Link`, `Allow` and `WWW-Authenticate`. `Set-Cookie`, `Location`, `Content-Length`, `Transfer-Encoding` and `Content-Encoding` are excluded. Values are printable ASCII up to 256 bytes (no header injection). Names are case-insensitive and canonicalized; two spellings of one name are rejected. Default `Content-Type` is `text/plain; charset=utf-8` so Go does not sniff. The default `X-Powered-By: PHP` of the login page is dropped for fixtures unless the fixture sets it.
- **Limits.** 64 entries, 8 KiB body, 16 headers, 256 byte paths, 1 MiB file (read through `io.LimitReader`, regular files only). Errors name the variable and the entry (`entry 3 (path "/x")`, path quoted and cut to 64 bytes).
- **When the file is read.** In `config.Load`, so `ran check-config` reports errors with exit 1. Only when `http` or `https` is in `RAN_TRAPS` (like `RAN_BANNER_SERVICES` for `banner`); otherwise the variable is ignored.
- **Why docker, kubernetes and mcp are excluded.** They embed `HTTPTrap` for the connection plumbing but replace the handler with API stubs whose answers (JSON-RPC, Docker and Kubernetes API shapes) must stay consistent. The fixture set is only built for the `http` and `https` protocols, so it is structurally absent for them.
- **No request data in responses.** The response is built from the fixture only. A test requests every built-in and a sample operator fixture with markers in the path, query, headers, cookie and Basic auth, and checks that none appear in the status line, headers or body. The built-in table is also validated with the operator loader and checked for IP addresses.
- **Built-in set.** `/.git/HEAD`, `/.git/config`, `/.env`, `/actuator/health`, `/actuator/env`, `/server-status`, `/phpinfo.php`, `/wp-json/`, `/robots.txt`, `/sitemap.xml`, `/.well-known/security.txt`. All content is invented (`example.com` for the one URL and mail address, placeholder key, `changeme`), no IP addresses. `/favicon.ico` and `/wp-includes/version` were left out: a favicon needs a binary body and the WordPress version file is PHP source that an HTTP server would not serve.
